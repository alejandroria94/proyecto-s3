Cómo se empaqueta, se orquesta y se verifica la plataforma completa

SeguridadauthestudiantescursosmatrículasDocker y pruebas

Propósito

Un sistema no está completo solo porque funciona dentro del IDE. Esta guía analiza cómo el proyecto se empaqueta en contenedores, cómo Docker Compose levanta los cinco servicios juntos y cómo se verifica el sistema completo con Swagger y con las pruebas automatizadas.

Cómo usar esta guía: el código ya está en el repositorio. Lea cada archivo, levante el sistema con Docker, ejecute la verificación y responda las preguntas de análisis. No hay que escribir código.

Paso 1 — El Dockerfile de un servicio

Los cinco servicios usan el mismo Dockerfile; solo cambia el puerto de EXPOSE:

Archivo: cursos-service/Dockerfile

FROM eclipse-temurin:21-jre
WORKDIR /app
ARG JAR_FILE=target/*.jar
COPY ${JAR_FILE} app.jar
EXPOSE 8083
ENTRYPOINT ["java","-jar","/app/app.jar"]
LíneaQué hace
FROM eclipse-temurin:21-jreParte de una imagen que solo trae el entorno de ejecución de Java 21 (sin compilador).
WORKDIR /appCarpeta de trabajo dentro del contenedor.
ARG JAR_FILE=target/*.jar y COPYCopia el .jar que Maven dejó en target/, sin importar su nombre exacto. Por eso hay que compilar antes de construir la imagen.
EXPOSE 8083Documenta el puerto en el que escucha el servicio.
ENTRYPOINTEl comando que se ejecuta al iniciar el contenedor.

Paso 2 — La orquestación con Docker Compose

Archivo: docker-compose.yml

services:
  auth-service:
    build: ./auth-service
    container_name: auth-service
    ports:
      - "8081:8081"

  estudiantes-service:
    build: ./estudiantes-service
    container_name: estudiantes-service
    environment:
      AUTH_SERVICE_URL: http://auth-service:8081
      MATRICULAS_SERVICE_URL: http://matriculas-service:8084
    depends_on:
      - auth-service
    ports:
      - "8082:8082"

  cursos-service:
    build: ./cursos-service
    container_name: cursos-service
    environment:
      AUTH_SERVICE_URL: http://auth-service:8081
      MATRICULAS_SERVICE_URL: http://matriculas-service:8084
    depends_on:
      - auth-service
    ports:
      - "8083:8083"

  matriculas-service:
    build: ./matriculas-service
    container_name: matriculas-service
    environment:
      AUTH_SERVICE_URL: http://auth-service:8081
      ESTUDIANTES_SERVICE_URL: http://estudiantes-service:8082
      CURSOS_SERVICE_URL: http://cursos-service:8083
    depends_on:
      - auth-service
      - estudiantes-service
      - cursos-service
    ports:
      - "8084:8084"

  calificaciones-service:
    build: ./calificaciones-service
    container_name: calificaciones-service
    environment:
      AUTH_SERVICE_URL: http://auth-service:8081
      MATRICULAS_SERVICE_URL: http://matriculas-service:8084
    depends_on:
      - auth-service
      - matriculas-service
    ports:
      - "8085:8085"
  • Nombres de servicio como direcciones: dentro de la red de Compose, http://auth-service:8081 llega al contenedor de auth. localhost dentro de un contenedor es el propio contenedor.
  • Variables de entorno: reemplazan los valores por defecto de application.yaml (por ejemplo, ${AUTH_SERVICE_URL:http://localhost:8081}). El mismo código funciona en local y en Docker.
  • depends_on: define el orden de arranque, pero no espera a que el otro servicio esté listo para responder.
  • Sin ciclos: estudiantes y cursos llaman a matrículas (E1), pero no declaran depends_on hacia ella porque matrículas ya depende de ellos y Compose no acepta ciclos.
  • ports: "8083:8083" publica el puerto del contenedor en el equipo, para usar Swagger desde el navegador.

Paso 3 — Levantar el sistema

cd auth-service && mvn clean package -DskipTests && cd ..
cd estudiantes-service && mvn clean package -DskipTests && cd ..
cd cursos-service && mvn clean package -DskipTests && cd ..
cd matriculas-service && mvn clean package -DskipTests && cd ..
cd calificaciones-service && mvn clean package -DskipTests && cd ..
docker compose up --build
Primer arranque: la primera petición que cruza varios servicios puede tardar varios segundos (arranque en frío de Feign y Hibernate). Si recibe un 502 apenas levantó el sistema, espere unos segundos y repita.

Paso 4 — Las pruebas automatizadas

Cada servicio tiene pruebas en src/test/java. Ejecútelas con mvn test dentro de cada carpeta:

ServicioClases de pruebaCasosTipo

matriculas-serviceMatriculaServiceImplTest, MatriculaControllerSecurityTest8Unitaria y web con seguridad (@WebMvcTest)

Ninguna prueba necesita otros servicios en ejecución: las llamadas remotas se reemplazan por mocks. Los reportes quedan en target/surefire-reports/.

Preguntas de análisis

  1. ¿Por qué dentro de Docker se usa http://auth-service:8081 y no http://localhost:8081?
  2. depends_on no espera a que un servicio esté listo. ¿Qué problema puede causar y cómo se resolvería (por ejemplo, con healthcheck)?
  3. Explique el resultado de la verificación 5. ¿Qué cambiaría para que los datos sobrevivan a un reinicio?
  4. El Dockerfile copia un .jar ya compilado. ¿Qué ventajas tendría compilar dentro de Docker (Dockerfile multi-stage)?
  5. Las 27 pruebas se ejecutan sin levantar ningún servicio. ¿Qué tipo de errores detectan y cuáles no pueden detectar?
