E4 · Mis matrículas

Guía de análisis: autorizar por dueño del recurso, no solo por rol

E2 CuposE1 IntegridadE4 Mis matrículasE3 Calificaciones

Qué resuelve esta extensión

Hasta el Lab 07 la autorización era solo por rol: un ADMIN puede todo, un DOCENTE consulta, un ESTUDIANTE ve cursos. Pero "un estudiante puede ver sus matrículas" no se puede expresar con roles: todos los estudiantes tienen el mismo rol y cada uno debe ver solo lo suyo. Eso es autorización por dueño del recurso.

La solución: el token del estudiante lleva su estudianteId, y GET /api/matriculas/mias usa ese dato del token, nunca un parámetro enviado por el cliente.

UsuarioGET /api/matriculasGET /api/matriculas/mias
ADMIN / DOCENTE200, todas403 (no es estudiante)
ESTUDIANTE403200, solo las propias
Cómo usar esta guía: el código ya está en el repositorio. Recorra los pasos con el proyecto abierto, ejecute la verificación y responda las preguntas de análisis. No hay que escribir código.

Solo el usuario estudiante tiene estudianteId (el estudiante 1). Para ADMIN y DOCENTE es null.

Paso 2 — El dato viaja dentro del token

Archivo: auth-service/src/main/java/co/edu/authservice/util/JwtUtils.java

package co.edu.authservice.util;

import io.jsonwebtoken.Claims;
import io.jsonwebtoken.JwtBuilder;
import io.jsonwebtoken.Jwts;
import io.jsonwebtoken.SignatureAlgorithm;
import io.jsonwebtoken.security.Keys;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Component;

import javax.crypto.SecretKey;
import java.nio.charset.StandardCharsets;
import java.util.Date;

@Component
public class JwtUtils {
    @Value("${app.jwt.secret}")
    private String secret;

    @Value("${app.jwt.expiration-ms}")
    private long expirationMs;

    private SecretKey getKey() {
        return Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));
    }

    public String generateToken(String username, String role, Long estudianteId) {
        Date now = new Date();
        Date expiration = new Date(now.getTime() + expirationMs);
        JwtBuilder builder = Jwts.builder()
                .setSubject(username)
                .claim("role", role)
                .setIssuedAt(now)
                .setExpiration(expiration);
        // E4: el claim solo existe para usuarios asociados a un estudiante
        if (estudianteId != null) {
            builder.claim("estudianteId", estudianteId);
        }
        return builder.signWith(getKey(), SignatureAlgorithm.HS256).compact();
    }

    public Claims parseToken(String token) {
        return Jwts.parserBuilder().setSigningKey(getKey()).build().parseClaimsJws(token).getBody();
    }
}

Archivo: auth-service/src/main/java/co/edu/authservice/service/AuthServiceImpl.java

public TokenValidationResponse validate(String authorization) {
    if (authorization == null || !authorization.startsWith("Bearer ")) {
        throw new InvalidTokenException("Debe enviar un token Bearer válido");
    }

    try {
        String token = authorization.replace("Bearer ", "");
        var claims = jwtUtils.parseToken(token);
        return new TokenValidationResponse(
                true,
                claims.getSubject(),
                claims.get("role", String.class),
                claims.get("estudianteId", Long.class)
        );
    } catch (Exception ex) {
        throw new InvalidTokenException("Token inválido o expirado");
    }
}
Detalle técnico: JJWT lee los números pequeños del token como Integer. Por eso se usa claims.get("estudianteId", Long.class), que hace la conversión. Un cast directo ((Long) claims.get("estudianteId")) lanzaría ClassCastException.

Paso 3 — Matrículas guarda un principal propio

En los demás servicios, el filtro guarda en el SecurityContext solo el nombre del usuario. Matrículas necesita además el estudianteId, así que usa un objeto propio:

Archivo: matriculas-service/src/main/java/co/edu/matriculasservice/security/UsuarioAutenticado.java

package co.edu.matriculasservice.security;

import java.security.Principal;

/**
 * Principal que el filtro guarda en el SecurityContext. Además del usuario y el rol,
 * conserva el estudiante asociado (E4) para autorizar por dueño del recurso.
 */
public record UsuarioAutenticado(String username, String role, Long estudianteId) implements Principal {

    @Override
    public String getName() {
        return username;
    }
}

Archivo: matriculas-service/src/main/java/co/edu/matriculasservice/security/AuthValidationFilter.java

UsernamePasswordAuthenticationToken authentication = new UsernamePasswordAuthenticationToken(
        new UsuarioAutenticado(validation.getUsername(), validation.getRole(), validation.getEstudianteId()),
        null,
        List.of(new SimpleGrantedAuthority(validation.getRole()))
);
SecurityContextHolder.getContext().setAuthentication(authentication);

Como UsuarioAutenticado implementa Principal, authentication.getName() sigue devolviendo el nombre del usuario y el resto del código no se entera del cambio.

Paso 4 — La regla de seguridad y su orden

Archivo: matriculas-service/src/main/java/co/edu/matriculasservice/config/SecurityConfig.java

// E4: debe ir ANTES de la regla general; gana la primera regla que coincide
.requestMatchers(HttpMethod.GET, "/api/matriculas/mias").hasAuthority("ESTUDIANTE")
.requestMatchers(HttpMethod.GET, "/api/matriculas/**").hasAnyAuthority("ADMIN", "DOCENTE")

Spring Security evalúa las reglas en orden y aplica la primera que coincide. /api/matriculas/mias también coincide con /api/matriculas/**; si la regla general estuviera primero, el estudiante recibiría siempre 403.

Paso 5 — El endpoint toma el id del token

Archivo: matriculas-service/src/main/java/co/edu/matriculasservice/controller/MatriculaController.java

// E4: el estudiante se toma del token, nunca de un parámetro de la petición
@GetMapping("/mias")
public ResponseEntity<ApiResponse<List<MatriculaDTO>>> misMatriculas(
        @Parameter(hidden = true) @AuthenticationPrincipal UsuarioAutenticado usuario) {
    if (usuario == null || usuario.estudianteId() == null) {
        throw new AccessDeniedException("El usuario no tiene un estudiante asociado");
    }
    return ResponseBuilder.ok("OK", handler.listarPorEstudiante(usuario.estudianteId()));
}

@AuthenticationPrincipal entrega el objeto que el filtro guardó. El endpoint no recibe ningún id: así es imposible pedir las matrículas de otra persona. Si un usuario ESTUDIANTE no tuviera estudiante asociado, se lanza AccessDeniedException, que el manejador global convierte en un 403 con el formato uniforme:

Archivo: matriculas-service/src/main/java/co/edu/matriculasservice/controller/GlobalExceptionHandler.java

@ExceptionHandler(AccessDeniedException.class)
public ResponseEntity<ApiErrorResponse> handleAccessDenied(AccessDeniedException ex, HttpServletRequest request) {
    return ResponseEntity.status(HttpStatus.FORBIDDEN)
            .body(ApiErrorResponse.of(ex.getMessage(), "AUTH_FORBIDDEN", HttpStatus.FORBIDDEN.value(), request.getRequestURI()));
}

Preguntas de análisis

  1. Otro diseño posible sería GET /api/matriculas?estudianteId=1 abierto al rol ESTUDIANTE. ¿Qué vulnerabilidad tendría? (Busque el término IDOR.)
  2. ¿Qué pasaría si se invirtiera el orden de las dos reglas del paso 4? Compruébelo mentalmente con la petición del estudiante.
  3. El estudianteId viaja en el token. Si un administrador cambia la asociación usuario–estudiante, ¿cuándo se entera matrículas? Compare con consultar la asociación en cada petición.
  4. ¿Por qué UsuarioAutenticado es un record que implementa Principal? ¿Qué se rompería si fuera un objeto cualquiera?
  5. ¿Podría un estudiante fabricar un token con otro estudianteId? ¿Qué lo impide?
