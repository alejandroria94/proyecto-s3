Guía de análisis: cómo proteger datos relacionados cuando están en bases de datos distintas

Qué resuelve esta extensión

En un monolito, una llave foránea impide borrar un curso que tiene matrículas. En microservicios cada servicio tiene su propia base de datos y esa llave no existe: en la versión base se podía eliminar un estudiante o un curso con matrículas activas, y esas matrículas quedaban apuntando a un registro que ya no existía.

Con E1, antes de eliminar, estudiantes-service y cursos-service le preguntan a matriculas-service cuántas matrículas activas hay.

SituaciónAntesCon E1
Eliminar un curso con matrículas activas200: matrículas huérfanas409 Conflict "No se puede eliminar: el curso tiene N matrícula(s) activa(s)"
Eliminar un estudiante sin matrículas activas200200
Eliminar con matriculas-service caído200502: si no se puede verificar, no se elimina
Cómo usar esta guía: el código ya está en el repositorio. Recorra los pasos con el proyecto abierto, ejecute la verificación y responda las preguntas de análisis. No hay que escribir código.

Flujo de una eliminación

DELETE /api/cursos/3 (token de ADMIN)
   │
   ▼
cursos-service ── GET /api/matriculas/activas/conteo?cursoId=3 (mismo token) ──► matriculas-service
   │                                                                              │
   │◄──────────────────────────── {"success":true,"data":2} ──────────────────────┘
   ▼
¿data > 0?  sí → 409 Conflict      no → se elimina (200)      error remoto → 502
Dependencia circular: matrículas consulta a cursos (para verificar que existe) y ahora cursos consulta a matrículas (para verificar que no tiene matrículas). Funciona, pero acopla los dos servicios en ambas direcciones. Es la decisión de diseño más importante de esta extensión y se discute en las preguntas de análisis.

Paso 1 — Matrículas publica un conteo

Archivo: matriculas-service/src/main/java/co/edu/matriculasservice/controller/MatriculaController.java

// E1: lo consultan estudiantes-service y cursos-service antes de eliminar
@GetMapping("/activas/conteo")
public ResponseEntity<ApiResponse<Long>> contarActivas(
        @RequestParam(value = "estudianteId", required = false) Long estudianteId,
        @RequestParam(value = "cursoId", required = false) Long cursoId) {
    return ResponseBuilder.ok("OK", handler.contarActivas(estudianteId, cursoId));
}

Archivo: matriculas-service/src/main/java/co/edu/matriculasservice/service/MatriculaServiceImpl.java

public long contarActivas(Long estudianteId, Long cursoId) {
    // E1: exactamente uno de los dos filtros
    if ((estudianteId == null) == (cursoId == null)) {
        throw new BusinessException("Envíe exactamente uno de los parámetros: estudianteId o cursoId");
    }
    return estudianteId != null
            ? repository.countByEstudianteIdAndEstado(estudianteId, EstadoMatricula.ACTIVA)
            : repository.countByCursoIdAndEstado(cursoId, EstadoMatricula.ACTIVA);
}

El endpoint exige exactamente un filtro: con ninguno o con los dos responde 400. Devuelve un número, no la lista: quien pregunta solo necesita saber si hay matrículas y cuántas.

El endpoint queda bajo la regla GET /api/matriculas/** (ADMIN, DOCENTE). Como solo un ADMIN puede eliminar y su token se reenvía, la consulta siempre está autorizada.

Paso 2 — El cliente Feign en estudiantes-service

Archivo: estudiantes-service/src/main/java/co/edu/estudiantesservice/client/MatriculasClient.java

import org.springframework.cloud.openfeign.FeignClient;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestParam;

@FeignClient(name = "matriculasClient", url = "${matriculas-service.url}")

    @GetMapping("/api/matriculas/activas/conteo")
    RemoteApiResponse<Long> contarActivasPorEstudiante(@RequestParam("estudianteId") Long estudianteId);
}

A diferencia de los clientes del Lab 06 (@PathVariable), este envía un parámetro de consulta con @RequestParam: la URL resultante es /api/matriculas/activas/conteo?estudianteId=1.

Archivo: estudiantes-service/src/main/java/co/edu/estudiantesservice/dto/RemoteApiResponse.java

package co.edu.estudiantesservice.dto;

/**
 * Copia local del contrato de respuesta de los otros servicios: {success, message, data}.
 */
public class RemoteApiResponse<T> {
    private boolean success;
    private String message;
    private T data;

    public boolean isSuccess() { return success; }
    public void setSuccess(boolean success) { this.success = success; }
    public String getMessage() { return message; }
    public void setMessage(String message) { this.message = message; }
    public T getData() { return data; }
    public void setData(T data) { this.data = data; }
}

Archivo: estudiantes-service/src/main/java/co/edu/estudiantesservice/config/FeignAuthPropagationConfig.java

package co.edu.estudiantesservice.config;

import feign.RequestInterceptor;
import jakarta.servlet.http.HttpServletRequest;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpHeaders;
import org.springframework.web.context.request.RequestAttributes;
import org.springframework.web.context.request.RequestContextHolder;
import org.springframework.web.context.request.ServletRequestAttributes;

/**
 * Reenvía el token del usuario en cada llamada Feign saliente.
 */
@Configuration
public class FeignAuthPropagationConfig {

    @Bean
    public RequestInterceptor authTokenPropagationInterceptor() {
        return requestTemplate -> {
            if (requestTemplate.headers().containsKey(HttpHeaders.AUTHORIZATION)) {
                return;
            }
            RequestAttributes attributes = RequestContextHolder.getRequestAttributes();
            if (attributes instanceof ServletRequestAttributes servletAttributes) {
                HttpServletRequest request = servletAttributes.getRequest();
                String authorization = request.getHeader(HttpHeaders.AUTHORIZATION);
                if (authorization != null && !authorization.isBlank()) {
                    requestTemplate.header(HttpHeaders.AUTHORIZATION, authorization);
                }
            }
        };
    }
}

Es la misma configuración de matriculas-service: sin ella, la llamada llegaría sin token y matrículas respondería 401.

Archivo: estudiantes-service/src/main/resources/application.yaml

Paso 3 — La regla al eliminar

Archivo: estudiantes-service/src/main/java/co/edu/estudiantesservice/service/EstudianteServiceImpl.java

public void eliminar(Long id) {
    Estudiante estudiante = obtenerPorId(id);
    // E1: no se elimina un estudiante que todavía tiene matrículas activas
    long activas = contarMatriculasActivas(id);
    if (activas > 0) {
        throw new ConflictException("No se puede eliminar: el estudiante tiene " + activas + " matrícula(s) activa(s)");
    }
    repository.delete(estudiante);
}

Archivo: estudiantes-service/src/main/java/co/edu/estudiantesservice/service/EstudianteServiceImpl.java

private long contarMatriculasActivas(Long estudianteId) {
    try {
        RemoteApiResponse<Long> response = matriculasClient.contarActivasPorEstudiante(estudianteId);
        if (response == null || !response.isSuccess() || response.getData() == null) {
            throw new RemoteServiceException("matriculas-service no devolvió el conteo de matrículas");
        }
        return response.getData();
    } catch (FeignException ex) {
        throw new RemoteServiceException("No fue posible verificar las matrículas del estudiante (código remoto " + ex.status() + ")");
    }
}

La regla está en el servicio, no en el controlador, porque es una regla de negocio. Si matrículas no responde, se lanza RemoteServiceException y el estudiante no se elimina: ante la duda, el sistema prefiere no perder integridad.

Paso 4 — Nuevos códigos de respuesta

public class ConflictException extends RuntimeException {
    public ConflictException(String message) {
        super(message);
    }
}

Archivo: estudiantes-service/src/main/java/co/edu/estudiantesservice/controller/GlobalExceptionHandler.java

@ExceptionHandler(ConflictException.class)
public ResponseEntity<ApiResponse<Object>> handleConflict(ConflictException ex) {
    return ResponseEntity.status(HttpStatus.CONFLICT)
            .body(new ApiResponse<>(false, ex.getMessage(), null));
}

@ExceptionHandler(RemoteServiceException.class)
public ResponseEntity<ApiResponse<Object>> handleRemote(RemoteServiceException ex) {
    return ResponseEntity.status(HttpStatus.BAD_GATEWAY)
            .body(new ApiResponse<>(false, ex.getMessage(), null));
}

409 Conflict indica que la petición es correcta pero choca con el estado actual de los datos: si primero se anulan las matrículas, la misma petición sí funciona.

Paso 6 — Docker Compose y la dependencia circular

Archivo: docker-compose.yml

estudiantes-service:
  build: ./estudiantes-service
  container_name: estudiantes-service
  environment:
    AUTH_SERVICE_URL: http://auth-service:8081
    MATRICULAS_SERVICE_URL: http://matriculas-service:8084
  depends_on:
    - auth-service
  ports:
    - "8082:8082"

Se agregó la variable MATRICULAS_SERVICE_URL, pero no un depends_on hacia matriculas-service: matrículas ya depende de estudiantes, y Compose rechaza los ciclos. Como el conteo solo se usa al eliminar, no hace falta que matrículas esté arriba cuando estudiantes arranca.

Verificación

Parta de la verificación de E2 (curso 3 con dos matrículas activas) o registre antes dos matrículas en el curso 3. Use un token de admin:

#AcciónResultado esperado
1GET /api/matriculas/activas/conteo?cursoId=3200 con "data": 2
2GET /api/matriculas/activas/conteo (sin filtro)400 "Envíe exactamente uno de los parámetros…"
3DELETE /api/cursos/3409 "No se puede eliminar: el curso tiene 2 matrícula(s) activa(s)"
4DELETE /api/estudiantes/1 (tiene una matrícula activa)409
5DELETE /api/estudiantes/50 (sin matrículas)200
6Matricular al estudiante 5 en el curso 2 y ejecutar DELETE /api/cursos/2409 "…tiene 1 matrícula(s) activa(s)"
7Anular esa matrícula y repetir DELETE /api/cursos/2200: sin matrículas activas, el curso se elimina
8Detener matriculas-service y ejecutar DELETE /api/cursos/1502 "No fue posible verificar las matrículas del curso…"; el curso sigue existiendo
Haga el paso 8 al final de todas las verificaciones. Con H2 en memoria, al detener matriculas-service se pierden sus matrículas, y las guías de E4 y E3 las necesitan.

Preguntas de análisis

  1. Dibuje las dependencias entre los cinco servicios del proyecto. ¿Qué ciclos aparecen? ¿Qué riesgos tiene un ciclo al desplegar o al cambiar un contrato?
  2. Una alternativa es la eliminación lógica: marcar el curso como inactivo en lugar de borrarlo, y que matrículas rechace cursos inactivos. Compare las dos opciones (acoplamiento, historial de datos, complejidad).
  3. Si matrículas no responde, la eliminación se rechaza (fail-closed). ¿Qué pasaría con la opción contraria (fail-open)? ¿Cuándo sería aceptable?
  4. Entre la consulta del conteo y el delete pasa un instante. ¿Podría registrarse una matrícula justo en ese momento? ¿Qué consecuencia tendría?
  5. ¿Por qué 409 y no 400? ¿Qué le dice cada código al cliente sobre lo que debe hacer?
