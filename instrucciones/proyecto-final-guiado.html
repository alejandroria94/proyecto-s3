Propósito del proyecto

El proyecto final consolida los aprendizajes del curso en una sola solución. Se entrega una plataforma académica terminada, construida con las mismas técnicas de los laboratorios, y el trabajo del estudiante es comprenderla a fondo: explicar cómo se articulan la autenticación, la seguridad, la arquitectura por capas, la comunicación entre servicios, la documentación y el despliegue.

Analizar un sistema real es una habilidad central de la ingeniería de software: antes de modificar un sistema hay que entender qué hace, por qué está construido así y qué riesgos tiene.

Flujo de trabajo: 1) clone el repositorio y ejecute el sistema siguiendo el README, 2) recorra las guías de análisis en el orden de la sección "Secuencia de análisis", 3) ejecute la verificación de cada guía y guarde evidencias, y 4) responda las preguntas de análisis citando el código.
No hay que escribir código. Cada guía muestra los archivos reales del repositorio. Si propone mejoras, descríbalas y justifíquelas en el informe.

Caso propuesto

Una institución académica requiere una plataforma para administrar estudiantes, cursos, matrículas y calificaciones. Para no mezclar toda la lógica en una sola aplicación, la solución se divide en cinco servicios: autenticación, estudiantes, cursos, matrículas y calificaciones. El sistema permite iniciar sesión, obtener un token y consumir operaciones protegidas según el rol del usuario.

Competencias a demostrar

Técnicas

  • Explicar la organización en controller, handler, service, repository y model.
  • Explicar el flujo de autenticación con BCrypt y JWT y la autorización por roles.
  • Seguir una petición a través de varios servicios comunicados con OpenFeign.
  • Relacionar cada regla de negocio con el código que la implementa.
  • Ejecutar y verificar el sistema con Swagger, Docker Compose y pruebas automatizadas.

Formativas

  • Justificar las decisiones de diseño y compararlas con alternativas.
  • Identificar riesgos y limitaciones (concurrencia, disponibilidad, acoplamiento).
  • Sustentar afirmaciones con evidencias y citas del código.
  • Comunicar los hallazgos de forma clara y ordenada.

Arquitectura del sistema

Cada microservicio mantiene la estructura trabajada en clase:

controller → handler → service → repository → model

Y los servicios se relacionan así (todas las flechas llevan el token del usuario):

                       ┌──────────────── auth-service (8081) ◄── todos validan el token
                       │
estudiantes (8082) ◄───┼──── matriculas (8084) ◄──── calificaciones (8085)
cursos      (8083) ◄───┘         ▲
      │                          │
      └── (E1) conteo de matrículas activas antes de eliminar ──┘

Cada servicio tiene su propia base de datos H2 en memoria y expone su propia documentación Swagger.

Secuencia de análisis

Paso 1. Clone el repositorio, compile y ejecute los cinco servicios siguiendo el README.md. Ejecute mvn test en cada uno.
Paso 2. Lea la guía de seguridad: todos los servicios usan las mismas piezas.
Paso 3. Analice auth-service.
Paso 4. Analice estudiantes-service: es la referencia de la arquitectura por capas.
Paso 5. Analice cursos-service comparándolo con estudiantes.
Paso 6. Analice matriculas-service, el servicio integrador.
Paso 7. Reinicie los servicios y analice las extensiones en orden: E2 → E1 → E4 → E3.
Paso 8. Levante el sistema con Docker y complete la guía de Docker, Swagger y pruebas.
Paso 9. Redacte el informe de análisis y prepare la sustentación.
Datos en memoria: las bases H2 se reinician con cada servicio. Cada guía indica desde qué datos parte su verificación.

Respuestas de error de negocio

Además de los errores de seguridad, los servicios responden con {"success": false, "message": ..., "data": ...} y el código HTTP correspondiente:

CódigoCuándo
400Datos inválidos (validación), JSON mal formado, parámetro con tipo incorrecto o regla de negocio incumplida (duplicados, matrícula ya anulada).
404El recurso o la ruta no existen.
405Método HTTP no permitido en esa ruta.
409Conflicto con los datos almacenados.
502Un servicio del que depende la operación no respondió correctamente.
Un 401 siempre significa un problema con el token. Si recibe un 401 con un token válido, revise que la ruta /error esté permitida en SecurityConfig.

Respuestas de seguridad uniformes

Los servicios protegidos ahora responden con una estructura JSON uniforme cuando ocurre un error de autenticación o autorización. Esto mejora la trazabilidad, facilita las pruebas en Swagger y permite que el cliente identifique con claridad si el problema fue un token ausente, un token inválido o un rol insuficiente.

{
  "success": false,
  "message": "Debe enviar un token Bearer válido",
  "errorCode": "AUTH_HEADER_MISSING",
  "status": 401,
  "path": "/api/recurso",
  "timestamp": "2026-04-11T15:30:00"
}
  • AUTH_HEADER_MISSING: no se envió el encabezado Bearer.
  • TOKEN_INVALID: el token no es válido o no contiene rol.
  • TOKEN_VALIDATION_ERROR: no fue posible validar el token contra auth-service.
  • AUTH_FORBIDDEN: el usuario está autenticado, pero no tiene el rol necesario.
